# stepcache 설계

상태: 확정. 만드는 순서는 [plan.md](plan.md)에 있다.

## 1. 풀려는 문제

문서 변환 파이프라인에는 비싼 단계가 여럿 있다. 그림 하나를 예로 들면 다음과 같다.

```
docx 속 그림 바이트 → Murex 렌더 → PNG → OCR → VLM(alt·LaTeX) → TypeSafe 확인 → 최종 치환
```

- 이 중 한 단계가 바뀌었을 때(Murex 수정, 프롬프트 수정, 모델 교체) **영향받은 그림의 영향받은 단계만** 다시 돌아야 한다.
- 앞 단계를 다시 돌렸는데 **결과 바이트가 같으면** 뒤 단계는 캐시를 그대로 쓴다.
- 같은 그림이 여러 문서에 나오면 한 번만 처리한다.
- 어떤 문서가 옛 단계로 만들어졌는지 **조회**할 수 있어야, 영향받은 문서만 다시 처리할 수 있다. 결과를 캐시하지 않는 싼 단계(개요 엔진 등)도 이 조회에는 들어가야 한다.

같은 생각이 프로젝트마다 따로 만들어지곤 한다. 이 라이브러리는 그것을 한곳으로 모은다. 흔한 모양은 둘이다.

- 검사 코드·설정 파일의 해시, 외부 도구의 바이너리·소스 지문, 출력 폴더 단위의 stale 표시를 프로젝트 안에 손으로 만든다.
- 결과 폴더 안에 캐시 파일을 둔다(그림 sha + 모델 + 프롬프트 revision). 결과 폴더를 지우고 다시 만들면 캐시도 함께 사라져 비싼 호출이 모두 다시 돈다.

stepcache는 3GPP·Word·Murex를 모른다. 단계가 무엇을 계산하는지는 각 패키지와 애플리케이션이 정하고, stepcache는 **키, 저장, 재사용, 무효화, 출처 기록**만 맡는다.

## 2. 용어

이 문서와 코드에서는 아래 뜻으로만 쓴다.

| 용어 | 코드 | 뜻 |
|---|---|---|
| 단계 | `Step` | 이름(무엇을 계산하나) + 단계 버전(무엇으로 계산하나). |
| 단계 버전 | `Version` | 단계가 무엇으로 계산하는지: run 모듈 해시, 선언한 파일, 외부 도구 지문, 수동 번호. 단계에 붙는 값이고 입력과는 무관하다. |
| 입력 | `inputs` | 단계를 한 번 부를 때 넣는 이름 붙은 값. blob이거나 JSON 값이다. 설정(크기, crop)도 입력이다. |
| blob | `Blob` | sha256으로만 가리키는 바이트. 단계 출력(렌더한 PNG, OCR 텍스트)이 blob 저장소에 들어간다. |
| 키 | `key` | `H(이름, 단계 버전, 입력)`. 같은 키면 같은 계산이다. |
| 레코드 | `Record` | 키 하나에 레코드 하나. 출력(blob sha와 JSON 값), 상태, 결과 해시를 담는다. |
| 결과 해시 | `result_sha` | 레코드 출력 전체를 바이트 그대로 해시한 값. 1바이트만 달라도 다르다. |
| 적중 / 미스 | hit / miss | 키의 레코드가 있고 그 blob이 모두 남아 있으면 적중, 아니면 미스. 미스면 계산해서 레코드를 쓴다. |
| 거절 / 오류 | refused / error | 거절: 단계가 결정적으로 내린 "처리할 수 없음". 레코드로 저장한다. 오류: 일시적 실패. 저장하지 않는다. |
| 무효화 | `invalidate` | 레코드를 지운다. 다음 실행이 같은 키로 새로 계산한다. |
| subject | | 매니페스트가 붙는 결과물 단위. 문서 하나다. 이름은 애플리케이션이 정한다. |
| 매니페스트 | `Manifest` | subject 하나가 기댄 `(단계, 단계 버전, 키, 결과 해시)` 목록. |
| stale | | subject를 다시 처리해야 하는 상태(5.2). |
| 레코드 들여오기 | `import_records` | 이미 있는 결과를 레코드로 등록하는 것. |
| 정리 | `cleanup` | 저장소가 상한보다 커졌을 때, 오래 쓰이지 않은 큰 레코드와 blob부터 지우는 것. |

무효화는 **레코드**에 하는 동작이고, stale은 **subject**의 상태다. 무효화된 레코드에 기댄 subject가 stale이 된다.

## 3. 단계

### 3.1 단계와 단계 버전

```python
render = Step(
    name='murex.render',
    version=Version.of(
        files=Version.files(murex_source_dir, ['cli/**', 'vendor/**', 'Cargo.lock']),
        tools={'murex': murex_fingerprint, 'fonts': fonts_sha256},
        rev='1',                       # 아래로 잡히지 않는 로직 변경에만 손으로 올린다
    ),
    run=render_one,                    # (inputs) -> Outputs | Refused
)
```

단계 버전은 네 부분으로 이뤄진다.

- `code`: `run`(과 `run_batch`)이 정의된 **모듈 파일**의 해시. 라이브러리가 자동으로 넣는다. 끄려면 `code=False`. 파일을 찾을 수 없는 함수(대화형 셸에서 만든 함수, C로 만든 함수)면 `Step`을 만들 때 오류를 낸다. 조용히 빼지 않는다.
- `files`: 단계가 읽는 그 밖의 소스·설정 파일(상대 경로 + 바이트). `run` 모듈이 import하는 다른 모듈과 데이터 파일은 **선언한 것만** 들어간다. 자동으로 넣는 것은 `code` 하나뿐이고, 나머지를 빠뜨리지 않는 것은 단계 작성자의 책임이다.
- `tools`: 외부 프로그램·모델의 지문(바이너리 해시, 모델 ID, 패키지 버전). 값은 애플리케이션이 정한다. 플랫폼마다 다른 바이너리 해시를 넣으면 mac 개발기와 Linux 서버가 캐시를 공유하지 않는다. 공유하려면 소스 지문이나 버전 문자열을 넣는다.
- `rev`: 위로 잡히지 않는 변경용 수동 번호.

단계 버전은 구성 요소별로 저장한다(`{'code': sha, 'files': {path: sha}, 'tools': {...}, 'rev': '1'}`). 비교와 키에는 이것의 해시 `version_sha`를 쓴다. 구성 요소는 `versions` 테이블에 버전마다 한 번만 저장하고(6.1), 레코드와 매니페스트는 `version_sha`만 가진다. `files`가 수백 개인 버전을 레코드마다 복사하지 않으려는 것이다. 단계 버전은 프로세스 시작 시 한 번 계산하고 고정한다. 실행 중에 도구를 바꿨다면 프로세스를 다시 띄운다.

이름이 키에 들어가는 이유: 단계 버전은 "무엇으로" 계산하는지만 말한다. `vlm.alt`와 `vlm.math`가 같은 모듈·같은 모델을 쓰고 프롬프트만 코드 안 상수로 다르면 버전이 같을 수 있다. 이름이 "무엇을" 계산하는지를 구별한다. 정말 같은 계산이면 같은 이름의 한 단계로 둔다. 두 애플리케이션이 같은 이름·같은 버전의 `murex.render`를 쓰면 캐시를 공유한다. 단계 이름을 바꾸면 그 단계의 캐시는 처음부터 다시 쌓인다.

### 3.2 기록만 하는 단계 (`cache=False`)

```python
outline = Step(name='docxoutline', version=Version.of(tools={'threegpp-outline': ver}), run=..., cache=False)
```

- 매번 실행하고 결과를 저장하지 않는다. 키도 계산하지 않는다.
- subject 안에서 실행하면(5.1) 매니페스트에 `(단계, 단계 버전)`만 남는다. 그래서 "옛 개요 엔진으로 만든 문서"를 stale로 찾을 수 있다.
- 문서 훑기(텍스트·헤딩·표)와 개요 엔진처럼, 계산은 싸지만 출처는 추적해야 하는 단계에 쓴다.

### 3.3 입력과 키

- 입력은 이름 → 값의 사전이다. 값은 `Blob(bytes)` 또는 JSON 값이다.
- 키에서 blob은 sha256으로, JSON 값은 그대로 들어간다. 파일 경로·이름은 키에 들어가지 않는다.
- `key = sha256(canonical_json(['stepcache/1', name, version_sha, inputs]))`
  - 정규화: 키 정렬, UTF-8, 공백 없음. 부동소수는 단계가 정한 자릿수로 반올림해 넘긴다. 라이브러리가 임의로 반올림하지 않는다.
  - `'stepcache/1'`은 키 형식 버전이다. 정규화 규칙이 바뀌면 올린다. 옛 레코드는 적중하지 않고 정리(8)로 지워진다.
- 출력은 이름 → `Blob` 또는 JSON 값이다.
  - **JSON 값**은 레코드 행 안에 저장된다. 그림 종류 답, 게이트 통과 여부 같은 짧은 값용이다. 상한 4 KiB, 넘으면 오류.
  - **blob**은 blob 저장소에 들어가고 레코드에는 sha만 남는다. OCR 텍스트, alt 텍스트처럼 길어질 수 있는 텍스트와 PNG가 여기 해당한다. 목록 형태의 출력은 단계가 JSONL blob으로 내보낸다.
- 입력 blob은 저장하지 않는다. 뒤 단계의 입력은 앞 단계 출력이라 이미 저장되어 있고, 첫 단계의 원본은 docx에 있다.

### 3.4 앞 단계 출력이 같으면 뒤 단계는 적중한다

뒤 단계의 입력은 앞 단계 **출력 blob의 sha**다. 앞 단계의 키가 아니다.

```
murex.render  key = H(render, v_murex2, {wmf: sha_W, size, crop})   → png: sha_P
ocr           key = H(ocr,    v_ocr,    {png: sha_P})               → text: sha_T
vlm.alt       key = H(vlm,    v_vlm,    {png: sha_P, ocr: sha_T})
```

Murex가 v3이 되면 render 키는 모두 바뀌어 모든 그림을 다시 렌더한다. 다시 렌더한 PNG의 sha가 `sha_P`와 같은 그림은 ocr·vlm 키가 그대로라 적중한다. sha가 바뀐 그림만 뒤 단계를 다시 돈다. 따로 이름 붙인 장치가 아니라 키를 이렇게 만든 결과다.

## 4. 레코드와 실행

### 4.1 레코드

```
Record {
  key,                                # 기본 키. 키 하나에 레코드 하나
  step, version_sha,                  # 구성 요소는 versions 테이블에 있다(3.1, 6.1)
  inputs,                             # 사람이 따라가기 위한 사본(키 재계산용 아님)
  status: 'ok' | 'refused',
  outputs: {name: blob:sha | value},  # refused면 비어 있다
  refusal: {reason, detail} | null,
  result_sha,                         # status + outputs + refusal의 정규화 JSON 해시
  created_at, duration_ms, producer,  # 진단용. producer: 호스트·패키지 버전·들여오기 여부
  last_used_at,                       # 정리(8)용
  input_key                           # 내부 인덱스: H(이름, 입력). explain이 옛 버전 레코드를 찾을 때만 쓴다
}
```

**레코드는 무효화할 때와 blob이 사라졌을 때만 바뀐다.** 둘 다 레코드를 지우고, 다음 실행이 같은 키로 새 레코드를 쓴다. 그 밖에는 처음 쓴 결과가 계속 유지된다. 비결정 단계(LLM, OCR)도 같다. 같은 입력에는 첫 답이 계속 쓰이고, 그래서 같은 문서를 다시 변환해도 같은 마크다운이 나온다.

### 4.2 실행 한 번

```python
cache = StepCache(SqliteStore('cache/stepcache.db', files='cache/blobs'))

res = cache.run(render, inputs={'wmf': Blob(data), 'size': ..., 'crop': ...})
res.hit                                 # True: 적중
res.status                              # 'ok' | 'refused'
res.outputs['png'].sha256, res.outputs['png'].read()
```

1. 키를 계산하고 레코드를 찾는다. 레코드가 있고 출력 blob이 모두 있으면 적중이다. 레코드는 있는데 blob이 없으면 그 레코드를 지우고 미스로 본다. 지우지 않으면 3~4단계에서 `put_if_absent`가 깨진 옛 레코드를 돌려준다.
2. 미스면 실행 중 표시를 남기고(6.2) 단계를 실행한다. 다른 worker가 이미 표시했으면 그 결과를 기다린다.
3. 출력 blob을 먼저 쓰고, 레코드를 `put_if_absent`로 쓴다.
4. **`put_if_absent`는 저장소에 남은 레코드를 돌려주고, `run`은 언제나 그것을 결과로 돌려준다.** 다른 worker가 같은 키를 먼저 썼다면 그 레코드다. 그래서 LLM 단계를 두 worker가 동시에 계산해도 뒤 단계와 매니페스트는 같은 답을 본다.

### 4.3 거절과 오류

- 단계는 거절이면 `Refused(reason, detail=None)`를 돌려주고, 오류면 예외를 던진다. 라이브러리는 둘을 추측하지 않는다.
- 거절은 `status='refused'` 레코드로 저장되고 다시 묻지 않는다. 단계 버전이 바뀌면 키가 바뀌므로 자연히 다시 판단한다.
- `cache.run`은 거절에서 예외를 던지지 않는다. `res.status`로 갈라 처리하는 것은 호출자 몫이다.
- 오류는 레코드를 남기지 않고 호출자에게 그대로 올라간다. 다음 실행에서 다시 시도된다.

### 4.4 일괄 실행

Murex, 수식 게이트처럼 여러 입력을 한 번에 돌리는 단계가 있다.

```python
results = cache.run_many(step, [inputs1, inputs2, ...])
```

- 키를 모두 계산해 적중은 바로 채우고, **미스만 모아** 단계의 `run_batch(inputs_list)`를 한 번 부른다.
- `run_batch`는 순서대로 `Outputs | Refused | Exception`의 리스트를 돌려준다. Exception인 것은 저장하지 않고, 나머지는 4.2의 3~4단계대로 저장한다.
- `run_many`는 순서대로 결과를 돌려준다. 오류인 것은 `res.error`에 예외를 담는다. 멈출지는 호출자가 정한다.
- `run`과 `run_many`는 동기 API다. `run_batch` 안의 동시성(스레드, asyncio)은 단계가 처리한다. async 코드에서 단계 하나를 부르는 길은 `async_run`이다(4.7).

### 4.5 무효화

- `cache.invalidate(step, key)`는 레코드를 지운다. 다음 `run`이 같은 키로 새로 계산한다.
- 단계 전체를 다시 묻고 싶으면 무효화가 아니라 단계 버전(`rev`, 프롬프트, 모델)을 바꾼다.

### 4.6 설명과 통계

- `cache.explain(step, inputs)`는 실행하지 않고 키와 적중 여부를 돌려준다. 미스라면 같은 이름·같은 입력의 다른 버전 레코드를 `input_key`로 찾아, 단계 버전이 어느 구성 요소에서 달라졌는지(`files['cli/main.rs']`, `tools.murex` 등) 보여 준다.
- 통계: 한 `StepCache`가 단계별로 적중, 미스, 거절, 오류 수를 센다.

### 4.7 async 실행

```python
res = await cache.async_run(vlm_alt, inputs={'png': Blob(png), 'ocr': Blob(text)})   # 단계의 run이 async def
```

- `async_run`은 `run`과 같은 순서(4.2)로 동작하고 결과도 같다. 단계 실행만 `await`하고, 다른 worker의 결과를 기다리는 동안 이벤트 루프를 막지 않는다.
- 조회, 실행 중 표시, 레코드 쓰기는 동기 DB 호출이다. 1 ms 미만이라 이벤트 루프에서 그대로 부른다.
- `run`, `run_many`, `async_run`은 같은 두 내부 동작("조회하고 표시하기", "결과 쓰기")을 감싼다. 표시와 대기는 한 곳에만 있다. 표시 해제는 단계를 실행하는 곳마다 `finally`로 한다.
- 단계의 `run`이 `async def`면 `async_run`으로만 부른다. `run`으로 부르면 오류다.
- subject 세션에도 `s.async_run`이 있다(5.1).
- `run_many`의 async 판은 없다. 호출자가 `async_run`을 `asyncio.gather`로 묶는다.

있는 이유: LLM·OCR 같은 외부 호출 단계는 흔히 `async def`이고, 항목 하나 안에서 여러 단계가 `await`로 이어진다. 동기 `run`은 이벤트 루프 안에서 그런 단계를 부를 수 없다.

## 5. 매니페스트와 stale

캐시만으로는 "어떤 문서가 옛 Murex로 만들어졌나"를 알 수 없다. 그래서 subject마다 매니페스트를 남긴다.

```
Manifest {
  subject: 'tdoc:R1-2609206' | 'spec:38.331-i60',
  produced_at,
  source: sha | null,                  # 애플리케이션이 넣는 원본 지문(선택)
  entries: [ {step, version_sha, key | null, result_sha | null}, ... ]   # cache=False 단계는 key·result_sha가 null
}
```

subject마다 최신 매니페스트 하나만 둔다.

### 5.1 만들기

```python
with cache.subject('tdoc:R1-2609206', source=docx_sha) as s:
    s.run(outline, ...)            # cache=False: (단계, 단계 버전)만 기록
    r = s.run(render, ...)         # 적중이든 실행이든 (키, 결과 해시)를 기록
    s.run_many(ocr, ...)
```

- `s.run`, `s.run_many`, `s.async_run`은 `cache`의 것과 같고, 쓰인 레코드를 매니페스트 항목으로 모은다.
- `with` 블록이 정상으로 끝날 때만 매니페스트를 저장한다. 예외로 끝나면 아무것도 쓰지 않는다. 이전 매니페스트가 남아 그 subject는 계속 stale로 보이고, 다시 처리 대상이 된다.
- 한 subject 세션을 여러 스레드가 같이 써도 된다.

### 5.2 stale 조회

```python
cache.stale_subjects(pipeline=[outline, render, ocr, vlm_alt], complete=True)
# -> [(subject, [reason, ...]), ...]
```

subject는 다음 중 하나라도 해당하면 stale이다.

- `version`: 매니페스트의 `version_sha`가 지금 그 단계의 버전과 다르다. 이유에 달라진 구성 요소를 담는다.
- `record`: 매니페스트가 가리키는 키의 레코드가 없거나(무효화됨), 레코드의 `result_sha`가 매니페스트와 다르다(무효화 뒤 다른 문서가 다시 계산함).
- `missing_step`: `complete=True`일 때만 따진다. `pipeline`의 단계가 매니페스트에 없다(파이프라인에 단계가 새로 생김).

`pipeline`에 없는 단계의 항목은 무시한다. 원본이 바뀌었는지(`source`)는 애플리케이션이 비교한다.

예: 그림 X가 문서 A와 B에 있다. `vlm.alt` 키 K의 결과 해시가 `r1`이고, A와 B의 매니페스트에는 `(K, r1)`이 있다.

1. K를 무효화한다. 레코드가 없어지므로 A와 B 모두 stale이다.
2. B를 다시 처리한다. K만 새로 계산되어 `r2`가 되고(LLM 답은 거의 항상 바이트가 다르다), 나머지는 적중한다. B는 `(K, r2)`가 되어 stale이 아니다.
3. A는 아직 `(K, r1)`이므로 stale이다. A를 다시 처리하면 K는 `r2`로 적중하고, LLM을 다시 부르지 않는다.

stale인 subject를 다시 처리해도 실제로 도는 것은 키가 바뀌었거나 무효화된 것뿐이다.

## 6. 저장소

### 6.1 인터페이스

저장소는 **DB 하나 + 큰 blob용 폴더 하나**다. v1의 구현은 `SqliteStore(path, files=dir)` 하나이고, 한 머신의 로컬 디스크 전용이다.

SQLite는 프로세스가 달라도 쓰기 트랜잭션을 한 번에 하나만 허용한다. 그래서 실행 중 표시(`INSERT ... ON CONFLICT DO NOTHING`)와 `put_if_absent`(쓰기 트랜잭션 하나 안의 INSERT와 SELECT)는 같은 머신의 여러 프로세스 사이에서 원자적이다. 8개 프로세스가 같은 순간에 같은 키 20,000개를 표시하게 한 실측에서 키마다 한 프로세스만 성공했고 잠금 오류는 없었다(macOS, 1.2초).

`PostgresStore(dsn, files=dir)`(extra `stepcache[postgres]`)는 쓰는 곳이 생기면 추가한다. 저장소 인터페이스와 테스트 묶음은 구현을 하나 더 붙일 수 있게 둔다. 쓰는 곳이란 다음과 같은 경우다.

- worker가 두 호스트 이상에서 돈다. 예: 워커 컨테이너를 두 번째 머신에도 띄운다. SQLite의 잠금은 같은 커널 안에서만 통한다.
- DB 파일을 둘 곳이 NFS·SMB 같은 네트워크 파일 시스템뿐이다.
- 짧은 단계를 많은 worker가 돌려서, 한 줄로 서는 쓰기의 대기 시간이 단계 실행 시간에 견줄 만큼 길어진다. 쓰기 한 번은 1 ms 미만이라, 초 단위로 걸리는 단계(VLM, 렌더)를 worker 몇 개가 돌리는 지금은 해당하지 않는다.

한 머신의 로컬 파일 시스템에서 도는 worker와 CLI는 어느 것도 해당하지 않는다.

DB 테이블:

| 테이블 | 내용 |
|---|---|
| `records` | 키당 한 행(4.1). 짧은 JSON 출력 값은 이 행 안에 있다. |
| `blobs` | blob마다 한 행: `sha, size, last_used_at, data`. 256 KiB 이하는 `data`에 바이트가 들어가고(SQLite BLOB), 그보다 크면 `data`가 비어 있고 바이트는 `files/ab/cdef…`(sha로 정해지는 경로) 파일에 있다. |
| `versions` | 단계 버전마다 한 행: `version_sha`와 구성 요소(3.1). stale 이유의 "달라진 구성 요소"도 여기서 찾는다. |
| `manifests` | subject당 한 행(5): `produced_at`, `source`. |
| `manifest_entries` | 매니페스트 항목마다 한 행: `subject, step, version_sha, key, result_sha`. stale 조회를 SQL 한 번으로 한다. 매니페스트를 쓸 때 한 트랜잭션에서 그 subject의 옛 항목을 지우고 새 항목을 넣는다. |
| `claims` | 실행 중 표시(6.2). |
| `meta` | `schema_version`. |

- blob 인터페이스는 `put(bytes) -> sha`, `get(sha)`, `has(sha)`, `touch(sha)`, `delete(sha)`다. DB에 넣을지 파일로 쓸지는 저장소가 크기를 보고 정한다. 단계와 레코드는 위치를 모른다.
- 큰 blob 파일은 임시 파일 + rename으로 원자적으로 쓰고, 그다음 `blobs` 행을 넣는다. 그래서 행이 있으면 파일도 있다.
- 기준값(4 KiB, 256 KiB)은 설정으로 빼지 않은 상수다. 그림마다 OCR·alt·LaTeX 텍스트가 파일로 흩어지지 않게 하려는 값이다.
- 저장 순서는 blob, 레코드, 매니페스트다. 중간에 죽으면 가리키는 곳 없는 blob만 남고, 정리가 치운다.
- SQLite는 WAL 모드와 `busy_timeout`으로 연다. 쓰기는 `BEGIN IMMEDIATE`로 시작하고, 단계를 실행하는 동안에는 트랜잭션을 열어 두지 않는다. 쓰기는 한 번에 하나씩이지만 한 머신의 여러 프로세스가 같이 쓸 수 있다. NFS·SMB 같은 네트워크 파일 시스템 위에서는 파일 잠금을 믿을 수 없으므로 쓰지 않는다.
- 지원 환경은 macOS와 Linux(ARM·x86), 그리고 그 위의 Docker 컨테이너다. Windows는 지원하지 않는다(`flock`이 없다).
- 여러 컨테이너가 같은 volume이나 bind mount의 캐시를 함께 써도 된다. ARM Linux 컨테이너 둘이 4개 프로세스씩 같은 키 20,000개를 표시한 실측에서 키마다 한 프로세스만 성공했고, 다른 컨테이너의 owner가 SIGKILL로 죽은 것도 잠금 파일로 바로 알아냈다.
- **mac의 Docker Desktop에서 호스트 프로세스와 컨테이너가 같은 캐시를 함께 쓰면 안 된다.** bind mount가 VM 경계를 넘는 공유 파일 시스템이라 잠금이 호스트와 컨테이너 사이에 전달되지 않는다. 실측에서 컨테이너가 쥔 잠금을 호스트가 보지 못했고, 양쪽이 동시에 쓴 DB는 깨졌다(`database disk image is malformed`). 캐시 하나는 호스트 프로세스들만 쓰거나 컨테이너들만 쓴다.
- Docker Desktop의 bind mount 위에 둔 DB는 컨테이너끼리는 정확했지만 named volume보다 3배쯤 느렸다(같은 실측 4.4초, 1.4초).
- 저장소 테스트는 구현을 인자로 받는 한 묶음으로 쓴다. 구현이 늘면 같은 묶음을 그대로 돌린다.

### 6.2 동시성

**같은 키를 동시에 계산하지 않는다.** 미스가 나면 실행하기 전에 "실행 중 표시"를 원자적으로 남긴다.

```
Claim { key, owner }                  # 키당 하나. 실행이 끝나면 지운다. owner: 표시를 남긴 프로세스의 잠금 파일 이름
```

1. 미스가 나면 `claim(key)`를 부른다. 표가 비어 있을 때만 들어간다(`INSERT ... ON CONFLICT DO NOTHING`). 표시를 남기면 레코드를 한 번 더 찾는다. 앞 worker가 조회와 표시 사이에 레코드를 쓰고 표시를 지웠을 수 있다. 레코드가 있으면 표시를 지우고 그것을 쓴다.
2. 표시를 남긴 worker만 실행한다. 레코드를 쓰거나(성공·거절) 예외가 나면 표시를 지운다.
3. 표시를 남기지 못한 worker는 레코드가 생길 때까지 기다린다. 표시가 사라졌는데 레코드가 없으면(앞 worker가 오류로 끝남) 1부터 다시 한다.
4. worker가 죽으면 표시가 남는다. 기다리는 worker는 owner가 살아 있는지 확인하고, 죽었으면 표시를 바로 가져가 직접 실행한다.
5. `run_many`는 미스를 모두 표시하고, 표시를 남긴 것만 `run_batch`로 돌린다. 다른 worker가 표시한 것은 끝에 기다려서 받는다.

owner가 살아 있는지는 **프로세스 잠금 파일**로 확인한다.

- 프로세스는 처음 표시를 남길 때 DB 파일 옆 폴더(`<DB 파일 이름>.locks/`)에 임의 이름의 잠금 파일을 만들어 `flock`으로 잡고, 끝날 때까지 쥔다. DB 하나에 프로세스마다 파일 하나다.
- 정상 종료하면 자기 잠금 파일을 지운다. 프로세스는 자기 잠금 파일을 만들 때 폴더를 한 번 훑어, 죽거나 `os._exit`로 끝난 프로세스의 파일을 지운다.
- owner 이름이 잠금 파일 이름 형식(16진수 32자)이 아니면 죽은 것으로 본다. DB에서 읽은 값으로 다른 파일을 열거나 지우지 않으려는 것이다.
- 기다리는 쪽은 owner의 잠금 파일을 잡아 본다. 잡히지 않으면 owner가 살아 있다. 잡히거나 파일이 없으면 owner가 죽은 것이다.
- 프로세스가 어떻게 죽든(SIGKILL 포함) 커널이 잠금을 푼다. pid로 확인하지 않는 이유는 pid가 재사용되기 때문이다. 컨테이너는 다시 뜰 때마다 pid를 작은 수부터 새로 매기므로, 죽은 worker의 pid를 새 worker가 다시 받는다.
- `fork`로 생긴 자식은 부모의 잠금을 물려받는다. 자식은 fork 직후 물려받은 잠금 파일 기술자를 닫고, 표시를 남길 때 자기 잠금 파일을 새로 만든다. 닫지 않으면 stepcache를 쓰지 않는 자식도 죽은 부모의 표시를 살아 있게 보이게 한다.
- 살아 있지만 멈춘 프로세스의 표시는 라이브러리가 풀지 않는다. job을 죽이는 쪽(supervisor)이 그 프로세스를 죽이면 그 순간 풀린다.

시간 제한(`claim_timeout`), 연장, 하트비트는 두지 않는다. owner가 살아 있는지 묻는 방법은 저장소 구현의 몫이고, 위는 `SqliteStore`의 방법이다. 표시가 실패하더라도 `put_if_absent`가 먼저 쓴 결과를 지키므로(4.2) 답은 갈라지지 않는다. 표시는 계산이 중복되는 것만 막는다.

이 방식이 필요한 이유: job을 돌리는 supervisor는 흔히 종료·배포 때 worker를 죽이고 그 job을 바로 다시 큐에 넣는다. 시간 제한 방식이면 다시 들어온 job이 죽은 worker가 남긴 표시에 걸려 제한 시간만큼 기다린다.

## 7. 레코드 들여오기

캐시를 처음 붙이면 비어 있어서 첫 실행에서 외부 호출이 몰린다. 그래서 이미 있는 결과를 레코드로 등록한다.

```python
cache.import_records(step, [(inputs, outputs), ...])
```

- 레코드는 **지금 단계 버전**으로 들어간다. "이 결과를 지금 단계의 결과로 인정한다"는 명시적 결정이다. `producer`에 들여온 레코드라는 표시가 남는다.
- 들일지는 호출자가 옛 기록의 메타데이터(모델, 프롬프트 rev)를 보고 정한다. 예: 옛 캐시 파일에서 모델과 프롬프트 rev가 지금과 같은 항목만 들인다.

## 8. 정리

정리의 목적은 저장소가 너무 커지지 않게 하는 것이다. 오래되었다는 이유만으로는 지우지 않는다. 석 달 전 문서의 그림이 새 문서에 다시 나오는 일이 흔하기 때문이다.

- 저장소 크기가 상한을 넘을 때만 지우고, 상한 아래로 내려오면 멈춘다.
- 지울 순서는 마지막 사용 시각과 크기를 함께 본다. 오래 쓰이지 않았고 큰 것부터 지운다.
- 어떤 매니페스트도 가리키지 않는 레코드를 먼저 지운다. blob은 그것을 가리키는 레코드가 없을 때 지운다.
- 마지막 사용 시각은 처음부터 적는다.
  - 레코드의 `last_used_at`은 적중할 때 갱신하되, 하루에 한 번까지만 쓴다.
  - blob의 `last_used_at`(`blobs` 행)도 같은 방식으로 갱신한다. 쓰는 쪽은 blob이 이미 있어 `put`을 건너뛸 때도 `touch(sha)`를 한다. 그래서 정리가 방금 다시 쓰인 blob을 지우지 않는다.
  - 그래도 레코드는 있는데 blob이 없으면 미스가 되어 다시 계산한다(4.2).
- `dry_run`이 기본이다. 지울 목록과 크기를 먼저 보여 준다.

| `vlm.alt` / `vlm.math` | PNG blob, OCR 텍스트 blob | 모델 ID, thinking 설정, 프롬프트 revision |
| `typesafe` | PNG blob, 후보 | 모델 ID |

- 문서 훑기는 싸서 항상 다시 한다. 마크다운은 "훑기 결과 + 그림별 최종 치환"으로 조립한다. 헤딩 로직만 바뀐 재변환은 그림 단계가 모두 적중하는 경우일 뿐이므로, "마크다운만 다시 변환하는" 별도 경로는 만들지 않는다.
- 캐시 저장소는 결과 폴더 바깥에 둔다. 결과 폴더를 지우고 다시 처리해도 적중한다.
- OCR을 캐시하면 VLM 키에 들어가는 OCR 텍스트도 안정된다. 캐시하지 않으면 OCR이 다시 돌 때 텍스트가 조금만 달라져도 VLM 캐시가 빗나간다.

## 10. 범위 밖

- 스케줄링·큐·재시도 정책: 애플리케이션 몫이다(job queue, CLI).
- 원격 실행, 분산 빌드.
- 단계 그래프 선언: 단계 사이의 연결은 호출 코드가 순서대로 `run`을 부르는 것으로 충분하다. DAG 선언 언어는 만들지 않는다.
- subject 원본이 바뀌었는지 판단하기(`source` 비교는 애플리케이션 몫).
- 출력의 의미 비교: 결과 해시는 바이트만 본다. 정규화가 필요하면 단계가 출력 전에 한다.
- `run_many`의 async 판(4.7).

## 11. 결정

### 정한 것

1. **PostgreSQL**: v1에는 없다. 쓰는 곳이 생기면 extra `stepcache[postgres]`로 추가한다(6.1에 쓰는 곳의 예). 그때도 스키마와 마이그레이션은 라이브러리가 관리한다.
2. **단계 버전의 파일 범위**: 선언한 파일 + `run` 모듈 자동 포함(`code`).
3. **비결정 단계**: 첫 답을 계속 쓴다. 다시 묻는 것은 단계 버전 변경이나 무효화로만.
4. **레코드**: 키 하나에 하나. 무효화할 때만 지워지고 다시 쓰인다. 매니페스트는 `(키, 결과 해시)`를 기록해 무효화 뒤의 변화를 잡는다.
5. **단계 = 이름 + 단계 버전**. 키에 둘 다 들어간다.
6. **설정은 입력의 일부**다. 따로 `params`를 두지 않는다.
7. **기록만 하는 단계**: `Step(cache=False)`.
8. **키 형식 버전**: 키 안의 `'stepcache/N'`. 형식이 바뀌면 이주 없이 새로 쌓는다.
9. **레코드 들여오기**는 지금 단계 버전으로만.
10. **입력 blob**은 저장하지 않는다. 옵션도 없다.
11. **매니페스트**는 `with cache.subject(...)` 블록이 모은다.
12. **거절**은 `res.status`로 알린다. 예외를 던지지 않는다.
13. **`run_many`의 일부 오류**는 항목별 결과(`res.error`)로만 돌려준다.
14. **같은 키를 동시에 계산하지 않는다**: 실행 전에 실행 중 표시를 원자적으로 남긴다(6.2). 죽은 worker의 표시는 프로세스 잠금 파일로 알아내 바로 가져간다. 시간 제한·연장·하트비트는 없다.
15. **정리**는 저장소 크기를 상한 아래로 유지하려고 한다. 지울 순서는 마지막 사용 시각과 크기를 함께 본다(8).
16. **스키마 이주**는 `stepcache migrate` 명령으로만 한다. 버전이 맞지 않으면 열 때 오류를 낸다. 빈 DB를 열 때 스키마를 만드는 것은 이주가 아니다. 쓰기 트랜잭션 하나 안에서 만들어, 여러 프로세스가 동시에 처음 열어도 한 번만 만들어진다.
17. **출력 저장**: 짧은 JSON 값(4 KiB 이하)은 레코드 행에, 그 밖은 blob. blob은 256 KiB 이하면 DB 행에, 크면 sha 경로의 파일에 둔다(6.1). JSONL 묶음 파일은 만들지 않는다. 묶음 안의 blob 하나를 지우거나 여러 worker가 동시에 덧붙이기 어렵기 때문이다.
18. **저장소 구현**: v1은 SQLite 하나(로컬 한 머신). 저장소 인터페이스와 테스트 묶음은 구현을 더 붙일 수 있게 둔다.
19. **async**: 단계 하나를 부르는 `async_run`만 둔다(4.7). 이름은 `arun`처럼 줄이지 않는다.
20. **라이선스**: Apache-2.0.

### 구현 때 확인할 것

- **blob 기준값**: 4 KiB(레코드 안 JSON 값 상한)와 256 KiB(DB에 넣는 blob 상한)는 실측 없이 정한 값이다. 첫 사용처의 실제 데이터로 출력 크기 분포와 파일 개수를 재서 확인한다.
- **운영 환경의 잠금**: 표시 경합과 잠금 파일은 macOS(APFS)와 Docker Desktop의 ARM Linux 컨테이너에서만 실측했다. 운영 환경의 파일 시스템에서는 같은 경합 테스트를 돌려 확인한다.

### 정할 것

- 정리의 세부: 크기 상한의 기본값, 마지막 사용 시각과 크기를 섞는 식, 상한을 넘은 채로 매니페스트가 가리키는 레코드만 남았을 때 그것까지 지울지. 정리를 만들 때 정한다.
